## 3) หน้าจอ (3 โซน)
1. **ค้นหา** ช่องเดียว พิมพ์ SO หรือ PO (วางได้หลายค่า ระบบดูเองว่าเป็นอะไร) · ตัวกรองเสริมพับไว้: ลูกค้า, สถานะ PCMS, Lab status, "เฉพาะที่มีพ่วง/โยก/สวม"
   - แถบสรุปทันที: จำนวน sale line · PO · พ่วงเข้า · โยกเข้า · สวม(คู่) · สถานะ PCMS แยกจำนวน · Lab ที่ไม่ใช่ `-`
2. **รายการ** จัดกลุ่ม **sale line (หัวกลุ่ม) → PO** · หัวกลุ่ม: SO/line, ปริมาณขาย+หน่วย, จำนวน PO, ป้ายพ่วงเข้า/โยกเข้า/สวม · แถว PO: PO, ปริมาณ, สถานะ PCMS (ERP ตัวเล็กถ้าไม่ตรง), LabStatus/LabNo, ป้ายโยกออก/พ่วงออก/สวมกับ PO ใด · แถวโยกเข้าและสวมเข้าแสดงใต้ line ปลายทางเป็นสีฟ้าอ่อน
   - **ไม่แสดง 51 คอลัมน์ของหน้า Detail** — เห็นเฉพาะ SO · PO · ปริมาณ · สถานะ · Lab + จำนวนที่เกี่ยวข้อง
3. **แผงด้านล่าง** (เลือก sale line หรือ PO แล้วโผล่) แท็บ **โยกขาย · สวมขาย · ประวัติ**
   - **โยก** (ตัวขับคือ sale line ที่ "รับ"): ตารางแถว (PO, ปริมาณ) แก้/ลบ/เพิ่มได้ + ติ๊ก "ทั้ง PO" แทนการพิมพ์ 0 + แสดงปริมาณที่เหลือของ PO ต้นทาง + ตรวจ: PO มีจริง · สถานะไม่ใช่ ยกเลิก/ตัดเกรดZ · ไม่ถูกสวม · หน่วยตรงกัน
   - **สวม** (ตัวขับคือ PO): เลือก PO คู่ → **พรีวิว** "line A จะได้ B · line B จะได้ A" → ยืนยัน · ปุ่ม "ยกเลิกการสวม" · ตรวจว่า PO ทั้งคู่ไม่ถูกโยก/สวมไปแล้ว
   - **ประวัติ**: ใคร · เมื่อไร · ค่าเดิม → ค่าใหม่ (อ่านจากแถวที่ปิดเป็น `X`)
4. กฎจาก `ux-ui-guideline.md`: ตัวหนังสือ ≥12px · เป้ากด ≥32px (≥44px บนแท็บเล็ต) · ปุ่มหลัก 1 ปุ่มต่อแผง · ปุ่มที่กดไม่ได้บอกเหตุผล · วันที่ dd/MM/yyyy · ยกเลิกซ้าย/ยืนยันขวา (Swal) · maxlength ตามคอลัมน์จริง · ห้ามใช้สีอย่างเดียวบอกสถานะ

## 4) "แก้แล้วตารางต้องอัปเดต" — ทำอย่างไร
- **หลักการ: เขียนผ่าน server แล้ว query อ่านใหม่ ไม่คำนวณใน JS** — หลังบันทึกโยก/สวม server คืน "ชุดผลกระทบ" = ทุก sale line/PO ที่เกี่ยวข้อง (ฝั่งรับ + ฝั่ง PO ต้นทาง + คู่สวม + แถว WaitLot) แล้วหน้าจอแทนที่แถวเหล่านั้นและไฮไลต์ 2–3 วินาที + ข้อความสรุป ("line 3 ได้ S6F157/1R · line 2 ได้ S6G055")
- แถบสรุปด้านบน (จำนวนพ่วง/โยก/สวม/สถานะ) คำนวณใหม่จากชุดข้อมูลเดียวกัน → ตัวเลขทุกที่ตรงกัน
- 🟡 **สถานะ PCMS (UserStatusCal/RP) หลังโยก/สวม:** flow เดิมของโยก/สวม **ไม่เรียก** proc คำนวณใหม่ (มีแต่ Stock Load ที่เรียก `execUpsertToTEMPUserStatusOnWebWithProdOrder`) สถานะจึงเปลี่ยนตอนรอบ sync :14/:44 ถ้าต้องการให้เห็นทันที ต้องเรียก proc ต่อ PO ที่เกี่ยวข้อง (ตัวเดียวกับที่แก้ไว้ 9 พ.ย. มี applock) — ต้องตัดสินใจและทดสอบ · ระหว่างนั้นหน้าใหม่ควรแสดงป้าย "สถานะอัปเดตรอบ sync ถัดไป" ข้าง PO ที่เพิ่งแก้

## 5) Backend (ให้เข้ากับโปรเจกต์: Spring MVC + JdbcTemplate + Gson/JSP)
- Controller ใหม่ (เช่น `/Relation`) · หน้า GET + endpoint ข้อมูล · **ทุก endpoint เช็คสิทธิ์ฝั่ง server** (แบบ `requireDetailPermit` / `canViewLog`) — บทเรียนจากช่องว่าง Detail/Log เมื่อ 2026-11-18
- **อ่าน:** DAO ใหม่ query ธรรมดาแบบ parameterized (`FromSapMainSale` ⟕ `FromSapMainProd` ⟕ `TEMP_UserStatusAuto`, `FromSapMainProdSale`, `ReplacedProdOrder`, `SwitchProdOrder`) รวมเป็นโมเดลใน Java · **ไม่ใช้ท่อ temp table ของหน้า Detail** (ไม่ต้องตามกฎ Pattern A/B/`dropAllTemp`) · ถ้า query ใดต้องเพิ่ม temp table ให้ทำตาม `.claude/rules/backend-patterns.md`
- **เขียน:** **เรียก logic เดิม** `PCMSDetailProcess.saveInputDetail` (case `replacedRemark`/`switchRemark`) เพื่อให้กติกา/ตรวจสอบ/ประวัติ/ตารางเดิม (`InputReplacedRemark`+`ReplacedProdOrder`, `InputSwitchRemark`+`SwitchProdOrder`) ตรงกับหน้า Detail ไม่มีกฎซ้ำสองที่ · แปลงแถว (PO, ปริมาณ) เป็นสตริง `PO=ปริมาณ,PO` ที่ logic เดิมรับ · แปลงข้อความ error ภาษาอังกฤษของ handler เป็นภาษาไทยที่ชั้นหน้าใหม่ (`iconStatus` E/W/I)
- **ห้าม:** แก้ตาราง `FromSap*` · UPDATE ทับค่า (ต้องปิดเป็น `X` + insert `O`) · เปลี่ยนสูตร Prod. Qty ของหน้า Detail (user ตัดสิน 2026-11-04 ให้คงตามขอบเขตการค้นหา)
- ⚠️ **หน้าใหม่ไม่แสดง "Prod. Qty"** ให้ชนกับหน้า Detail — แสดงเป็น `ปริมาณ PO · พ่วงออก · โยกออก` ดิบ พร้อมหน่วย เพื่อไม่ขัดการตัดสินใจเดิม · 🟡 ถ้าต้องการยอดคงเหลือต้องถามก่อนว่าจะตรงกับ Detail (ตามตัวกรอง) หรือต่อ PO

## 7) กรณีขอบที่ต้องออกแบบ
- sale line ไม่มี PO (WaitLot: "รอจัด Lot" / "Lot ขายแล้ว" / "ขาย stock") → ใช้ป้ายเป็นตัวแทน PO ตามที่ข้อมูลเดิมเก็บ (ตัวอย่าง: โยก 2,766 รายการผูกกับ "รอจัด Lot")
- PO สถานะ ยกเลิก/ตัดเกรดZ → ไม่นับยอด: เตือนก่อนโยก/สวม
- โยกด้วย Volume=0 → แสดง "ทั้ง PO (ปริมาณจริง)" เสมอ
- สวม: PO ต้องมี sale line หลัก · ห้ามเมื่อมีโยก/สวมค้าง · ยกเลิกสวมต้องคืนทั้งสองแถว
- ผู้ใช้ 2 คนแก้ line เดียวกัน: ระยะแรกพึ่งการปิด `X`+insert `O`; ระยะต่อไปส่ง `ChangeDate` ของแถวเดิมไปให้ server เทียบ แล้วปฏิเสธถ้าเปลี่ยนไปแล้ว
- ตารางกว้าง/จอเล็ก: รายการเลื่อนในกรอบสูง ~45% ของจอ แผงล่างติดขอบล่าง · ตรวจที่ 1366/1024/744px

## 9) คำถามที่ต้องตัดสิน 🟡 (คำตอบ/สถานะล่าสุดอยู่ที่หัวข้อ 10)

5. ช่องค้นหา: SO/PO พอหรือไม่ (ต้องมีลูกค้า/เลขใบสั่งซื้อ/LabNo ด้วยไหม)
6. สถานะที่แสดงเป็นหลัก = PCMS (คำนวณ) ใช่ไหม และให้ ERP เป็นรอง
7. จะ **เสริม** หน้า Detail หรือ **แทนที่** ช่อง ReplacedRemark/SwitchRemark ใน Detail ในอนาคต
8. ชื่อหน้า/เมนู (เสนอ: "PCMS - โยก/สวม")
9. ให้แก้เอกสารเก่าที่เรียก Replaced ว่า "สวม" ให้ตรงกับป้ายหน้าจอไหม

## 10) คำตอบจาก user (2026-11-19) และผลต่อการออกแบบ

| ข้อ | คำตอบ | ผลต่อการออกแบบ |

| 1 ใครแก้โยก/สวมได้ | ตอนนี้แก้ได้ทุกคนที่มีสิทธิ์ Detail · **รอสอบถามเพิ่ม** | ไม่เพิ่ม flag สิทธิ์ใน `Permits` (ไม่มี SQL patch สิทธิ์) แต่ให้มี **ตัวเช็คสิทธิ์เขียนจุดเดียวในโค้ด** (`canEditRelation(session)`) ทุก endpoint เขียนเรียกตัวนี้ → เปลี่ยนกติกาภายหลังจุดเดียว |
| 2 สถานะ PCMS หลังแก้ | **หลังโยกต้องอัปเดตทันที** (สวม: เสนอทำเหมือนกัน รอ user ยืนยัน) | ดู 10.1 |

### 10.1 อัปเดตสถานะทันทีหลังโยก — ตรวจจากนิยาม proc บน PRD (อ่านอย่างเดียว 2026-11-19)
- ใช้ proc ตัวเดียวกับ Stock Load: `spd_UpsertToTEMP_UserStatusOnWebWithProdOrder @ProductionOrder` (เรียกจาก `PCMSDetailProcess` ผ่าน `bgjService.execUpsertToTEMPUserStatusOnWebWithProdOrder`) แล้วอ่านสถานะใหม่จาก `TEMP_UserStatusAuto`
- proc คำนวณ **ทีละ PO** (`WHERE ProductionOrder = @ProductionOrder`) และอ่านความสัมพันธ์จาก `ReplacedProdOrder`/`SwitchProdOrder` → หลังบันทึกต้องเรียกกับ **ทุก PO ที่เกี่ยวข้อง**: PO เจ้าของแถว + ทุก PO ที่โยกเข้า/ออก (รวมตัวที่เพิ่งถูกลบ) · สวม: PO ทั้งคู่ (และคู่เก่าถ้าเปลี่ยนคู่)
- ⚠️ **proc ตัวนี้มี `NOT EXISTS` กัน insert ซ้ำ แต่ไม่มี `sp_getapplock` และไม่มี transaction** (ตัวรวม `spd_UpsertToTEMP_UserStatusOnWeb` ได้ applock ในฉบับ A2 เมื่อ 9 พ.ย.) → เรียกชนกับงานรอบ :14/:44 หรือสองคนเรียก PO เดียวกันพร้อมกัน อาจเกิดคีย์ซ้ำแบบเดิม (ต้นเหตุเดียวกับที่ตามแก้ใน `sql/2026-11-04_01_...`) · การโยก/สวมจะเรียกบ่อยกว่า Stock Load (45 ครั้ง/เดือน) หลาย PO ต่อครั้ง ความเสี่ยงจึงสูงขึ้น
- **ข้อเสนอก่อนเริ่มเฟส 2:** (ก) ให้ DBA ใส่ applock ตัวเดียวกับ A2 ในตัวต่อ PO (SQL บล็อกเดียวตาม `prd-sql-single-block-transaction.md` ทดสอบ DEV ก่อน) (ข) ฝั่งโค้ดเรียกต่อเนื่องทีละ PO ใน request เดียว ไม่ยิงขนาน (ค) ถ้า proc ล้มเหลว **การบันทึกโยก/สวมต้องยังสำเร็จ** และหน้าจอบอก "สถานะอัปเดตรอบ sync ถัดไป" แทนการล้มทั้งงาน (หลัก "ส่วนเสริมล้ม ห้ามลากส่วนหลักล้ม")
- ทดสอบบน DEV: บันทึกโยก → อ่านสถานะ → เทียบกับค่าที่งานรอบถัดไปคำนวณ ต้องตรงกัน (DEV ไม่มีข้อมูลโยก ต้องเตรียมข้อมูลทดสอบก่อน)

### 10.2 ยอดคงเหลือ — ออกแบบให้เห็นทั้งสองแบบ
ตัวอย่างจริง: SO 1107010287 line 200, PO S1K190 ผลิต 300 ให้ลูกค้า G TECH แต่ **พ่วง 100 ให้ SO 1107010283/100 ของ TW/PLC**
- หน้า Detail ปัจจุบัน (หักเฉพาะปลายทางที่อยู่ในขอบเขตค้น): ค้นเฉพาะ G TECH → **300** · ค้น G TECH + TW/PLC → **200**
- แบบ "ต่อ PO" (หักทุกปลายทางเสมอ): **200** ไม่ว่าค้นอย่างไร
- **ในหน้าใหม่ แต่ละแถว PO แสดง:** `ปริมาณ PO 300 · พ่วงออก 100 · โยกออก 0 · คงเหลือ (ทั้งระบบ) 200` และถ้าค่าตามขอบเขตที่ค้นอยู่ต่างกัน ขึ้นป้ายเล็ก `ตามที่ค้นนี้ 300 ⓘ` (tooltip: "หน้า Detail แสดง 300 เพราะ SO ปลายทาง 1107010283 ไม่อยู่ในผลค้นนี้") · ทั้งสองค่ามาจากชุดข้อมูลเดียวกัน คำนวณฝั่ง server (ขอบเขต = sale line ที่อยู่ในผลค้นปัจจุบัน)
- ค่าหลักที่แสดงใหญ่ = "คงเหลือ (ทั้งระบบ)" · ไม่ใช้คำว่า Prod. Qty · ไม่แก้สูตรของหน้า Detail (ยังเป็นไปตามที่ตัดสิน 2026-11-04)
- เฟส 1 (อ่านอย่างเดียว) ให้ฝ่ายแผนดูว่าแถวไหนสองค่าต่างกัน (กรอง "เฉพาะที่ต่างกัน") แล้วค่อยตัดสินว่าจะยึดแบบไหนเป็นหลักในหน้า Detail ภายหลัง

### 10.3 "เสริม" หรือ "แทนที่" Detail — ความหมาย
- **เสริม** = หน้าใหม่เพิ่มเข้ามาอีกหน้า · ช่อง ReplacedRemark/SwitchRemark ในหน้า Detail **ยังใช้ได้เหมือนเดิม** · ทั้งสองทางเขียนผ่าน logic เดียวกันลงตารางเดียวกัน ข้อมูลจึงตรงกัน · ข้อเสีย: มีสองที่ให้แก้ · หน้า Detail ที่เปิดค้างไว้จะไม่เห็นการแก้จนกว่าจะค้นใหม่
- **แทนที่** = วันหนึ่งปิดช่องกรอกโยก/สวมใน Detail (เหลืออ่านอย่างเดียว + ลิงก์ไปหน้าใหม่) · เหลือที่แก้ที่เดียว ผู้ใช้สับสนน้อยลง · ข้อเสีย: ถ้าหน้าใหม่ยังไม่ครอบคลุมเคส (เช่น แถว "รอจัด Lot") ผู้ใช้ทำงานไม่ได้
- **คำแนะนำ: เริ่มแบบเสริม** · ใช้หน้าใหม่ 2–4 สัปดาห์ · ถ้าฝ่ายแผนใช้เป็นหลักและไม่เจอเคสที่ทำไม่ได้ ค่อยตัดสินแทนที่ (ปิดทีละช่อง: Switch ก่อน เพราะใช้น้อย 10 ครั้ง/เดือน)
