# Code Quality — ตัวเลขจำกัดที่จับต้องได้

กฎนี้ใช้กับทุกโปรเจกต์ใน workspace (ไม่ผูก stack) — เสริม `.claude/rules/core-behavior.md`
("think before coding, simplicity, surgical changes") ด้วย**ตัวเลขอ้างอิง** เวลาต้องตัดสินใจว่า
"ควรแตกฟังก์ชัน/ไฟล์นี้ไหม" แทนการเดาเอาจากความรู้สึกล้วนๆ

ที่มา: เทียบกับ [lifedever/claude-rules](https://github.com/lifedever/claude-rules) (`base/core.md`,
`languages/java.md`) 2026-09-23 — เอาเฉพาะตัวเลข ไม่เอาแนวคิด "เจอ legacy code ต้อง refactor ตาม
standard ทันที" ของต้นฉบับมา เพราะ**ขัดกับหลักการ "surgical changes เท่านั้น" ของ workspace นี้โดยตรง**
(ดูหัวข้อ "ห้ามทำ" ด้านล่าง)

## ตัวเลขอ้างอิง (ไม่ใช่กฎบล็อกอัตโนมัติ — ใช้เป็นสัญญาณเตือนตัวเอง)

| อะไร | ขีดจำกัด | ทำอะไรเมื่อเกิน |
|---|---|---|
| ฟังก์ชัน/เมธอด | ≤ 30 บรรทัด (ไม่นับ whitespace/comment) | แตกเป็น helper function ที่ตั้งชื่อสื่อความหมาย |
| ไฟล์ | ≤ 300 บรรทัด | แยกตามความรับผิดชอบ (ไม่ใช่แยกมั่วๆ ให้สั้นลงเฉยๆ) |
| Nesting (if/for/callback ซ้อนกัน) | ≤ 3 ชั้น | ใช้ early return / แยก helper function |
| Parameter ต่อฟังก์ชัน | ≤ 4 | รวมเป็น object/record parameter |

## ห้ามทำ

- **ห้ามใช้ตัวเลขพวกนี้เป็นข้ออ้าง refactor โค้ดที่ไม่เกี่ยวกับงานที่สั่งเลย** — ถ้ากำลังแก้บั๊ก/เพิ่ม
  feature แล้วเจอไฟล์เก่าที่เกินขีดจำกัด **ไม่ต้องแตะทันที** นอกจากงานจะสั่งให้ refactor จริง (ตรงกับ
  หลักการ "surgical changes" ของ `core-behavior.md` — เคยเจอ pattern "เจอโค้ดเก่าต้องรื้อตาม standard
  ทันที" จาก repo อื่นแล้วพบว่าขัดกับ workflow ของ workspace นี้ที่เป็นระบบ legacy 10 ระบบ พังแล้วกระทบ
  ธุรกิจจริง ไม่ใช่ greenfield ที่ refactor บ่อยได้โดยความเสี่ยงต่ำ)
- ใช้เป็น**สัญญาณเตือนตัวเอง**เฉพาะตอนเขียนโค้ดใหม่/แก้โค้ดที่กำลังแตะอยู่แล้วเท่านั้น
