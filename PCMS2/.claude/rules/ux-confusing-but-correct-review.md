# UX Review: "ถูก Business Rule แต่ User งง" — Checklist

กฎนี้ใช้กับทุกโปรเจกต์ใน workspace — เสริม `.claude/rules/verify-in-browser-not-only-tests.md` (ซึ่งจับ
"พังทางฟังก์ชัน") ด้วยการจับ "**ทำงานถูกต้อง 100% ตาม spec แต่ user จริงงง/ตีความผิด/ไม่รู้จะทำอะไรต่อ**"
— บั๊กประเภทนี้ compile ผ่าน, เทสผ่าน, business logic ถูกทุกจุด แต่ยัง "พัง" ในมือ user เพราะเป็นปัญหาด้าน
cognition ไม่ใช่ correctness

บทเรียนจากเคสจริง: PrepareTax (2026-09-21) — review เปิดเบราว์เซอร์ดูบ้างแต่ไม่ครบทุกจุด พลาดทั้ง 3 แบบ:
(1) visual ผิดตา (2) interaction พังตอนใช้จริง (3) ถูก business rule แต่ user ใช้แล้วงง — ข้อ (3) เป็นข้อที่
static code review และ automated test ไม่มีทางจับได้เลยโดยธรรมชาติ ต้องมีขั้นตอนเฉพาะแยกออกมา

## ต้องทำ — ก่อนบอกว่า UI/UX work เสร็จ (โดยเฉพาะหน้าที่ non-technical user ใช้: บัญชี/operation)

### ขั้น 1 — Roleplay Naive User Pass (ทำก่อนเช็คความถูกต้อง)

เปิดหน้าจอจริงในเบราว์เซอร์ (ไม่ใช่อ่านโค้ด) แล้วสวมบทบาทเป็น user ที่:
- **ไม่รู้ business rule เบื้องหลัง** ที่ทำให้ค่านี้/สถานะนี้ออกมาแบบนี้
- **ไม่เคยเห็นหน้านี้มาก่อน** และไม่มีใครอธิบายให้ฟังล่วงหน้า

เดินตาม flow จริงแล้วถามตัวเองเป็นข้อๆ ก่อนเช็คว่า "ถูกไหม":
1. เห็นหน้าจอนี้ครั้งแรก รู้ทันทีไหมว่าต้องทำอะไรต่อ?
2. ค่า/label/badge ที่โชว์ — อ่านแล้วตีความตรงกับที่ระบบตั้งใจสื่อไหม หรือมีทางตีความผิดได้?
3. ถ้ากดปุ่ม/action ผิด จะรู้ทันทีไหมว่าเกิดอะไรขึ้น (error message เข้าใจได้ ไม่ใช่ error ทางเทคนิค)?
4. มีจุดไหนที่ "ถูกต้องตาม business rule" แต่ต้องรู้ context พิเศษถึงจะเข้าใจไหม (เช่น สถานะที่ล็อกเพราะ
   department ไม่ตรง แต่หน้าจอไม่บอกเหตุผล)?

**บันทึกจุดที่สะดุด/งงไว้ก่อน** อย่าเพิ่งข้ามไปเช็คว่า business logic ถูกหรือไม่ — สองเรื่องนี้แยกกัน
(ถูก logic ≠ เข้าใจง่าย)

### ขั้น 2 — เทียบกับ UX Heuristics มาตรฐาน

ใช้ฐานข้อมูล UX guideline จาก skill `ui-ux-pro-max` (มี 119 ข้อ) เช็คจุดที่สะดุดจากขั้น 1 ว่าตรงกับ
anti-pattern ที่รู้จักไหม โดยเฉพาะ:
- **Visibility of system status** — user รู้สถานะปัจจุบันของตัวเองไหม (กำลังรออนุมัติ/ถูกปฏิเสธ/ทำไปแล้ว)
- **Recognition over recall** — user ต้องจำอะไรจากหน้าก่อนไหมถึงจะใช้หน้านี้ได้
- **Error prevention/recovery** — ถ้าพลาด กู้คืน/แก้ไขได้ไหม รู้วิธีแก้ไหม
- **Consistency** — คำศัพท์/icon/สี ใช้ตรงกับหน้าอื่นในระบบเดียวกันไหม (เช่น badge สีเดียวกันแปลว่าอะไรต่างกัน
  ในแต่ละหน้าไหม — ถ้าใช่คือปัญหา)
- **Plain language** — ข้อความเป็นภาษาที่ user (ไม่ใช่ programmer) อ่านเข้าใจไหม (ดู
  `.claude/rules/user-manual-design.md` และ `feedback_nonprogrammer_docs_cut_jargon_not_add_detail`)

### ขั้น 3 — ตัดสินใจ + บันทึก

ทุกจุดที่เจอในขั้น 1-2 ต้องตัดสินใจอย่างใดอย่างหนึ่ง (ห้ามปล่อยผ่านเงียบๆ):
- **แก้ทันที** ถ้าแก้ง่าย (เปลี่ยนคำ, เพิ่ม tooltip, เพิ่มข้อความบอกเหตุผลของสถานะ)
- **แจ้ง user ก่อนแก้** ถ้าแก้แล้วกระทบ flow/business rule เดิม (เช่น ต้องเพิ่มขั้นตอนยืนยัน)
- **บันทึกไว้เป็น known issue** ถ้าตัดสินใจไม่แก้ตอนนี้ — ต้องระบุเหตุผลว่าทำไมยอมรับความงงนี้ได้ ไม่ใช่แค่ข้าม

บันทึกผลตาม `.claude/rules/session-logging.md` เสมอ ไม่ว่าจะแก้หรือไม่แก้

## ห้ามทำ

- ห้ามข้ามขั้น 1 ไปเช็คแค่ "business logic ถูกไหม" อย่างเดียว — logic ถูกไม่ได้แปลว่า UX ผ่าน
- ห้ามใช้ automated test/mvn test แทนขั้นตอนนี้ — เทสตรวจ correctness ไม่ตรวจว่า user เข้าใจไหม (คนละมิติกับ
  `.claude/rules/verify-in-browser-not-only-tests.md`)
- ห้ามสรุปเองว่า "user น่าจะเข้าใจ" โดยไม่เดินจริงในเบราว์เซอร์ด้วย fresh eyes — คนที่เขียนโค้ดเองมักมองข้าม
  จุดที่งงเพราะรู้ context อยู่แล้ว

## ข้อจำกัดที่ต้องยอมรับ

Roleplay ของ AI **ไม่แทนการทดสอบกับ user จริง** — ช่วยจับจุดสะดุดที่ชัดเจนได้ระดับหนึ่ง แต่ mental model ของ
user จริง (โดยเฉพาะฝ่ายบัญชี/operation ที่ไม่ใช่ programmer) อาจต่างจาก simulation นี้ ถ้าเป็นฟีเจอร์ที่กระทบ
งานสำคัญ ควรมีขั้นตอนให้ user จริงลองใช้ก่อน deploy ด้วย ไม่ใช่พึ่ง roleplay อย่างเดียว

## เมื่อไหร่ควรใช้ (สัญญาณ)

- เพิ่ม/แก้หน้าจอ, form, workflow status ใหม่ที่ non-technical user ใช้
- เพิ่ม error message หรือ validation message ใหม่
- มี badge/สถานะ/สี ที่สื่อความหมายบางอย่างให้ user ตีความ
- user เคยบ่นมาก่อนว่า "งง" "ไม่รู้ทำไม" "ไม่เข้าใจ" กับหน้าจอใดหน้าจอหนึ่ง (สัญญาณว่าโปรเจกต์นั้นเสี่ยงสูง
  ต้องเข้มกฎนี้เป็นพิเศษ)
